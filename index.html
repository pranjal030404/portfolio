From a device on a truck
to a dot on a map

A GPS tracking and IoT management system I built at Atrivis. Trackers in the field talk to it over raw TCP; a browser somewhere else shows where they are. These are the eight things in between.

  1. 01GPS deviceVehicle tracker in the field
  2. 02TCP serverCustom, long-lived connections

    Not HTTP

    Trackers open a socket and hold it. The server reads whatever arrives, whenever it arrives — there is no request to respond to.

  3. 03GT06 · Concox · PrithiviBinary frames

    Raw device frame

    Start bits, protocol number, payload, checksum — three device families, each with its own dialect of the same idea.

  4. 04ParserDecode and validate

    Decode

    Out comes position, speed, heading and status — the first point in the chain where the data means anything.

  5. 05Redis StreamsQueue between services

    Decouple ingestion

    Ingest never waits for processing. A slow consumer falls behind and catches up; it doesn't drop packets or take the socket server down.

  6. 06MicroservicesGeofences, alerts, trips
  7. 07MongoDBPosition history

    Persist

    Historical playback and route analytics both read from here.

  8. 08Live mapSocket.io · React · Leaflet

    Present

    Anything happening right now goes straight out to the dashboard, and the dot moves.

I like the parts of software you
don't notice when they're working.

I'm a software developer working on backend systems, real-time applications, device communication and production web platforms. The part I find most interesting is the layer between a device, a protocol, a backend, a database and the interface someone actually looks at — most software only has to worry about the last two.

That's meant writing TCP servers that speak GT06, Concox and Prithivi, putting Redis Streams between ingestion and processing, and keeping two MERN platforms running in production. Day to day it's Node.js, Express, React and MongoDB.
